# Contributing to pqc-ratchet

Thank you for your interest in contributing to `pqc-ratchet`! This document describes how to set up the project, which checks a change must pass, and how releases are made.

The repository holds two implementations of the same protocol: the Go module `github.com/usegoodkey/pqc-ratchet/go` in `go/` and the npm package `@usegoodkey/pqc-ratchet` in `ts/`. They share one binary wire format, one set of test vectors and one version.

## Development Setup

### Prerequisites

- Go 1.26 or newer (CI uses the latest 1.26 patch)
- Node.js `^20.19.0 || >=22.12.0` (CI uses Node.js 24)
- npm (the TypeScript package is locked with `ts/package-lock.json`)

### Installation

```bash
git clone https://github.com/usegoodkey/pqc-ratchet.git
cd pqc-ratchet

cd go && go test ./... && cd ..
cd ts && npm ci && npm test && npm run build && cd ..
```

## Project Layout

- `go/pqcratchet/` is the Go library. `go/pqcratchet/testdata/` holds the shared test vectors (`challenge_vectors.json`, `challenge_v2_vectors.json`), which the TypeScript specs read too.
- `go/cmd/challenge_vectors_gen/` regenerates the vectors; `go/cmd/interop_gen/` writes a standalone interop fixture.
- `go/DESIGN.md` has the design rationale and security analysis.
- `ts/src/index.ts` is the package's only entry point and must stay aligned with the package exports.
- `ts/scripts/interop_verify.mjs` is the TypeScript side of the interop test.
- `ts/build/` is generated by `npm run build` and is not committed.
- `demo/` is the static demo site. It is not part of a release.

## Development Workflow

### Code Quality

Before opening a pull request, run in `ts/`:

```bash
npm run lint          # oxlint
npm run format:check  # oxfmt
npm run typecheck     # tsc --noEmit
npm test              # vitest, runs once and exits
npm run build         # tsdown, also checks the package with attw
```

Fix lint and formatting issues with `npm run lint:fix` and `npm run format`. Use `npm run coverage` to produce a coverage report.

And in `go/`:

```bash
gofmt -l .            # must print nothing; fix with gofmt -w .
go vet ./...
go mod tidy -diff     # go.mod and go.sum must be tidy
go test -race ./...
go run golang.org/x/vuln/cmd/govulncheck@latest ./...
```

### Interop Test

`TestInteropGoTS` (`go/pqcratchet/interop_test.go`) checks both implementations against each other: Go generates identities and a fixture, the built TypeScript package decrypts Go's messages and encrypts replies, and Go decrypts those. It loads `ts/build/`, so build the package first:

```bash
cd ts && npm ci && npm run build && cd ..
cd go && PQC_REQUIRE_INTEROP=1 go test -run TestInteropGoTS -v ./pqcratchet/
```

Without `ts/build/` (or without `node`) the test skips; `PQC_REQUIRE_INTEROP=1`, which CI sets, makes it fail instead. Any change to the wire format, key derivation or the pairing code must change both implementations in the same pull request and keep this test and the shared vectors passing. Regenerate the vectors with `go run ./cmd/challenge_vectors_gen pqcratchet/testdata` from `go/` only when the change is intended.

### Testing

- Go: standard `testing` package, tests next to the code in `go/pqcratchet/`.
- TypeScript: Vitest. Put tests next to the code they cover as `ts/src/*.spec.ts` (public-API tests in `ts/src/index.spec.ts`).
- Cover new behavior and bug fixes with tests, in both implementations when both are affected.

### Build And Package Exports

The npm package is ESM-only; there is no CommonJS build, and CommonJS consumers load it through `require(esm)`. tsdown builds `ts/src/index.ts` into `ts/build/index.js` with `.d.ts` declarations. Output is unbundled, so every source module is emitted under `build/`, but only the root entry is reachable through `exports`. The syntax target comes from `engines.node`; do not set `target` in `tsdown.config.ts`.

`exports` and the legacy `main`/`module`/`types` fields in `ts/package.json` are generated by tsdown on every build and must not be edited by hand. Run `npm run build` and commit the regenerated `package.json`. CI fails if the build changes `package.json`.

Use named exports only (no `export default`) and no top-level `await`, so `require()` of the package keeps working on supported Node.js versions.

### Commit Messages

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Pull requests are squash-merged, so the pull request title becomes the commit message and must follow the same format.

```plain
type(scope): description

[optional body]

[optional footer]
```

Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `style`, `revert`. Use the scope `go` or `ts` when a change touches only one implementation.

Mark breaking changes with `!` after the type or scope (for example `feat(ts)!: ...`) and/or a `BREAKING CHANGE:` footer.

### Pull Requests

1. Fork the repository and create a branch from `main`.
2. Make your changes, with tests.
3. Run the checks listed above.
4. Open a pull request with a Conventional Commit title.

## Code Style

- Go: `gofmt` and `go vet` clean.
- TypeScript: follow the oxlint (`ts/.oxlintrc.json`) and oxfmt (`ts/.oxfmtrc.json`) configuration. Keep the lint config practical: prefer fixing the source over adding rules that only create churn, and disable a rule only when it fights the established style.
- Keep changes small and localized to the owning module.
- Prefer `Uint8Array`-based public APIs over Node.js-specific `Buffer` types; the TypeScript package runs in browsers too.
- Document every public exported type, function, method, and exported object member (TSDoc in TypeScript, doc comments in Go).
- The project is on 0.x: there are no API or wire stability guarantees yet, but mark breaking changes so they show up in the release notes.

## Releases

Releases are managed by [release-please](https://github.com/googleapis/release-please) (`release-please-config.json`, `.release-please-manifest.json`). Go and TypeScript share one version.

1. On every push to `main`, the **Publish** workflow first runs the **Test** workflow (TypeScript checks, Go checks and the interop test). Only when they pass does release-please open or update a `chore(release): vX.Y.Z` pull request that bumps `version.txt`, `ts/package.json` and `ts/package-lock.json`. The version comes from the commits: while on 0.x, a breaking change or `feat` bumps minor, and `fix`, `perf`, `build`, and `revert` bump patch. Other types, and commits that only touch `demo/` or `.github/`, do not trigger a release.
2. Merge the release pull request. release-please creates the `vX.Y.Z` tag and a GitHub Release with the notes from the pull request; the workflow then tags the same commit `go/vX.Y.Z` (the Go module lives in `go/`, so Go needs the prefixed tag), warms the Go module proxy, and moves the major tag (for example `v0`) when this is the newest release of that major.

To retry a failed tag push, run **Publish** manually from the `vX.Y.Z` tag. Set the optional `RELEASE_TOKEN` secret (PAT or GitHub App token) so the Test workflow runs on the release pull request.

Release notes live only in [GitHub Releases](https://github.com/usegoodkey/pqc-ratchet/releases); there is no `CHANGELOG.md`. Only `feat`, `fix`, `perf`, `build`, `revert`, and breaking changes are listed. Force a version with a `Release-As: x.y.z` line in a commit body. To fix the notes for a merged change, add a `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block with the corrected commit message to that pull request's description; edits to the release pull request description are overwritten when new commits land.
